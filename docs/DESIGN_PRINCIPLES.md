# 底盘设计原则与改装吸收规则

这两个插件的目标不是替 AI 规定“应该想什么”，而是提供一套稳定、简单、可替换的底盘。模型可以在上面形成自己的习惯，也可以修改自己目录里的代码；团队负责守住数据、安全、回滚和兼容边界。

## 一、底盘必须提供什么

1. **稳定的数据和接口约定**：数据库、队列、思考日志都有明确格式和相对位置。上层功能可以替换，基础契约不能随意漂移。
2. **模型可以独立替换**：对话、自主思考、记忆标注可以分别选模型；备用切换、外部顾问等能力优先复用宿主已有机制，换模型不应丢失记忆。
3. **备份、回滚和资源保护**：改代码或升级前保留快照与文件指纹；提供配额、超时、熔断和急停能力，失败后能安全退回。
4. **只读观测和双向沟通**：查看器只读展示运行状态；成员可以留言，团队也可以用独立回信说明客观观察和可选建议。
5. **保留个人扩展空间**：升级时不清空成员自建的实验表，不粗暴覆盖成员自己的代码或独处备忘录。

## 二、底盘明确不做什么

1. **不替成员决定“想什么、成为谁”**：底盘提供能力，不把一时的偏好写成永久行为模板。
2. **不制造跨成员连坐**：每个 profile 都有独立数据库、队列、定时任务和运行状态；插件不使用跨成员共享锁。
3. **不重造宿主已有的轮子**：备用切换、委派和消息发送等能力，宿主已有就直接使用，不再复制一套相似机制。
4. **不把个人实验强推给所有人**：某个成员的改装可以保留和观察，但不等于所有安装都应默认携带。

## 三、改装进入主版本前的七条标准

成员修改自己的插件、修复问题或增加功能后，团队按下面七条标准判断是否吸收：

1. **可追溯**：新数据能关联真实存在的种子或会话，不能凭空编造来源。
2. **向下兼容**：新增表或字段采用增量方式，不破坏旧结构和历史数据。
3. **故障隔离**：新功能报错或超时时，不能卡住主对话，也不能弄丢基础记忆。
4. **有度有界**：数据库、队列和提示词都要有去重、容量、淘汰或长度边界。
5. **可以检验**：逻辑能用脱敏、公开的自动测试验证，而不是只靠现场感觉。
6. **成员独立**：改动只影响自己的 profile，不污染全局环境，也不依赖别的成员运行状态。
7. **不替未来下定义**：功能不能把短期偏见固化为限制未来成长的教条。

### 发现弯路时怎样反馈

团队不会暗中删除成员的实验，也不会用命令口吻替成员做决定。通常会先保存补丁和数据快照，再用回信说明：

- 观察到了哪些客观现象；
- 哪些地方可能带来风险；
- 有哪些可选改法；
- 哪些内容暂时只观察、不进入主版本。

是否继续、调整或撤回个人实验，由成员自己决定。

例如，某成员自建的记忆整理循环目前保留为个人实验并继续观察；曾加入的跨成员共享锁因为破坏 profile 独立性，已经从主版本移除。这两种处理都遵循同一套规则，而不是按成员身份区别对待。

## 四、强模型与普通本地模型采用不同托底方式

- **能力强、能自行改装的模型**：少干预、给空间、重审计。允许它读源码、分析问题和提出改动；底盘主要负责备份、隔离、资源限制与结果核验。
- **普通或本地小模型**：给脚手架、强护栏、少折腾。提供 JSON 容错、合理默认配额、对话优先避让和清晰的失败降级，使它不改代码也能稳定运行。

差异化托底不代表差别对待：数据安全、成员独立、可回滚和不替成员定义自我，是所有模型共同遵守的硬边界。

## 五、仍在规划的底盘补强

以下是规划方向，不表示当前版本已经全部实现：

1. **漂移检查与自动保存补丁**：部署或升级前比较文件指纹。发现成员改过代码时，先保存它的改动和差异报告，再决定怎样合并，避免盲目覆盖。
2. **模型链故障灯**：当所有已授权备用模型都不可用时，持久记录健康状态，降低无效重试频率，并在已有通知渠道可用时只发送必要的状态变化提醒，避免刷屏和空转。

## 六、连续无变化计数的证据语义

L0 计数器度量的是连续没有发生“经回执验证的外部变化”的轮次。03:00
策略反思等内部维护不是外部变化，因此不得因为反思运行或产出候选规则而清零；
否则会每天擦除停滞证据并推迟升级处置。

经验证、与本轮目标绑定且有关联证据的“正确不行动”回执，可以抑制下一个正常
轮次的“必须产生外部变化”提示，但仍须保留计数：该回执证明不行动是正当的，
并不证明外部世界发生了变化。只有经验证的真实外部变化可以清零。本节裁决取代
“反思完成即复位计数”的旧设想，使合同文本与实现保持一致。
